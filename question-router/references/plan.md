## 1. 이 업무 유형으로 오는 신호 / 아닌 경우

이 업무 유형은 이미 방향이 정해진 안을 읽는 사람이 결정할 수 있는 문서(기획안·제안서·보고서·요청서·건의문·품의서·협업 제안 메일)로 옮기는 단계입니다. "기획안 써 줘", "보고서 초안", "제안서 만들어 줘", "요청서 정리해 줘", "건의문 초안", "팀장님께 올릴 문서"가 신호입니다. 문서를 읽고 누군가 승인·반려·보류 중 하나를 정한다는 점이 핵심입니다.

다음은 겉모습이 비슷해도 다른 업무 유형입니다.

- 아이디어 기획: 아직 무엇을 할지 고르는 중이면 이 업무 유형이 아닙니다. "무엇을 할지 고르는 것"이면 아이디어 기획, "고른 것을 승인받는 것"이면 기획안 작성입니다.
- 결과물 검토: 이미 쓴 초안의 오류·논리·문체를 점검하는 작업입니다. "새로 만드는가"이면 기획안 작성, "이미 있는 것을 고치는가"이면 결과물 검토입니다.

결재권자 없이 본인이 실행하는 계획(1인 운영 일정, 주차별 실행안, "실행 계획 정리해줘")도 이 업무 유형에서 다룹니다. 이 경우 2절의 "읽는 사람과 결정 사항"은 "실행자와 중간 점검에서 내릴 판단(유지·보완·전환)"으로 읽고, 형식 4(실행 계획)를 씁니다. 결재 문서용 항목(승인 요청, 예상 반론)은 넣지 않고, 그 자리에 목표 경로와 전환 조건을 둡니다.

## 2. 먼저 확인하는 것

| 확인 항목 | 왜 필요한가 | 없을 때 생기는 일 |
|---|---|---|
| 읽는 사람과 그 사람이 내릴 결정(승인·예산·인원·일정) | 결정 사항이 문서의 첫 문단과 구조를 정합니다[2][5] | 배경 설명이 길어지고 결론이 흐려집니다 |
| 근거 자료의 위치(첨부 파일·이전 보고·사용자가 아는 수치) | 자료 안의 수치만 쓰게 범위를 정합니다[3] | 없는 수치를 그럴듯하게 지어냅니다 |
| 제약(예산 상한·일정·인원·형식·분량) | 제약이 문서의 실행 가능성을 결정합니다 | 승인해도 실행할 수 없는 안이 나옵니다 |
| 참고할 형식(과거 통과된 문서·사내 양식) | 형식과 어투를 고정합니다[2] | 사내 관행과 다른 구조의 문서가 나와 다시 고칩니다 |

## 3. AI 초안이 결재를 못 받는 이유

두 가지로 나뉩니다.

첫째, 빈 정보를 채우는 경향입니다. 모델은 정보가 부족해도 문장을 완결된 형태로 만들려 하고, 그 과정에서 근거 없는 수치나 사례를 그럴듯하게 지어냅니다. Anthropic 공식 문서는 확인되지 않은 내용은 "모른다"고 말하게 허용하거나, 인용 근거가 없는 주장은 표시하고 제거하도록 지시할 것을 권장합니다[3]. 이 지시가 없으면 초안의 수치 중 어느 것이 자료에서 왔고 어느 것이 채워 넣은 것인지 사용자가 구분할 수 없습니다.

둘째, 읽는 사람이 없는 문서입니다. 누가 읽고 무엇을 결정하는지 지정하지 않으면 배경 설명이 길어지고 결론이 뒤로 밀립니다. 민토의 피라미드 원칙은 결재권자가 짧은 시간 안에 결론과 근거를 파악하도록 핵심 추천을 문서 맨 위에 두라고 말합니다[5]. 아마존의 6쪽 문서 관행도 회의 전에 읽는 사람이 결정하도록 서술형으로 완결된 문서를 요구합니다[4]. 읽는 사람의 유형(결론부터 보는 상사, 근거부터 보는 상사)에 따라 강조 순서를 바꾸라는 실무 안내도 같은 맥락입니다[8]. Anthropic 공식 문서는 지시의 배경(결과물이 어떻게 쓰이는지)을 설명하면 더 목표에 맞는 응답이 나온다고 설명합니다[2]. 같은 원리로 "이 문서는 예산 담당 임원이 승인 여부를 정할 때 읽는다"는 한 줄이 문체와 강조점을 바꿉니다.

역할 부여만으로는 이 문제가 풀리지 않습니다. Anthropic 공식 문서가 첫 번째로 꼽는 것도 역할이 아니라 명확하고 직접적인 지시입니다[1]. "당신은 20년 차 기획 전문가입니다" 같은 페르소나 문구가 사실 기반 과제의 성능을 일반적으로 높이지 않는다는 연구가 있습니다[6]. 역할 문구보다 독자·결정 사항·자료 위치 같은 구체적 맥락 지정이 결과에 직접 연결됩니다.

## 4. 질문 전략

### 4-1. 독자와 결정 사항을 먼저 지정

무엇을: 쓰게 하기 전에 이 문서를 읽는 사람이 누구이고, 그 사람이 무엇을 결정하는지 지시문에 넣습니다.
왜: 결과물의 용도를 설명하면 더 목표에 맞는 응답이 나옵니다[2]. 결정 사항이 정해지면 문서의 구조가 따라옵니다.
질문 문장:
```
이 문서는 팀장님이 예산 증액 여부를 결정할 때 읽을 기획안이야. 결정에 바로 쓸 수 있도록 결정 사항, 필요 금액, 대안을 구분해서 써줘.
```

### 4-2. 결론(요청 사항) 먼저 배치

무엇을: 배경·현황을 나열하기 전에 결정할 사항과 권고안을 문서 맨 앞에 놓게 합니다.
왜: 결론이 먼저 나와야 나머지 내용이 결론을 뒷받침하는 근거로 읽힙니다[5].
질문 문장:
```
결재권자가 첫 문단만 읽고 무엇을 승인해야 하는지 알 수 있게, 배경 설명보다 결론과 요청 사항을 맨 앞에 배치해서 써줘.
```

### 4-3. 자료와 지시를 구분하고 근거 위치 지정

무엇을: 참고 자료와 작성 지시를 구분해 제공하고, 어떤 자료에서 어떤 내용을 가져올지 지정합니다.
왜: 지시·맥락·입력을 구분하면 모호함이 줄고, 관련 인용을 먼저 추출한 뒤 그 인용에 근거해서만 쓰게 하면 지어내는 내용이 줄어듭니다[2][3].
질문 문장:
```
첨부한 지난 분기 실적 자료에서 이번 기획의 근거가 되는 수치만 먼저 인용하고, 그 인용에 없는 수치는 쓰지 말고 본문을 작성해줘.
```
```
본문의 주장마다 괄호로 근거 위치를 붙여줘. 첨부 파일이면 '파일명 p.○', 내가 말한 것이면 '사용자 입력', 근거가 없으면 '[확인 필요]'로 써줘.
```

### 4-4. 모르는 값은 빈칸으로

무엇을: 확인되지 않은 수치·일정·이름은 지어내지 말고 `[확인 필요]`로 남기게 합니다.
왜: "모른다"고 말하도록 허용하면 거짓 정보 생성이 줄어듭니다[3]. 빈칸이 보이는 초안이 채워진 초안보다 검토가 빠릅니다.
질문 문장:
```
예산 규모나 일정처럼 내가 아직 안 준 정보는 지어내지 말고 [확인 필요]로 남겨두고 나머지만 작성해줘.
```

### 4-5. 아웃라인 먼저, 본문은 확인 후

무엇을: 긴 문서를 한 번에 요청하지 않고 목차와 항목별 핵심 메시지를 먼저 받아 확인한 뒤 본문을 요청합니다.
왜: 복잡한 작업을 단계로 나누면 중간 결과를 검사하고 방향을 바꿀 수 있습니다[2]. 본문부터 쓰면 방향이 틀렸을 때 전체를 다시 씁니다.
질문 문장:
```
본문을 바로 쓰지 말고, 먼저 목차와 각 항목의 핵심 메시지 한 줄씩만 정리해줘. 확인 후에 본문을 요청할게.
```

### 4-6. 예시로 형식·어투 고정

무엇을: 과거에 통과한 기획안이나 원하는 형식의 예시를 함께 제공합니다.
왜: 예시 제공은 출력 형식·어투·구조의 일관성을 확보하는 방법으로 공식 문서가 안내합니다[2].
질문 문장:
```
지난번에 결재 통과된 이 기획안 형식을 참고 예시로 주니까, 같은 항목 구성과 어투로 이번 건을 써줘.
```

### 4-7. 대안과 하지 않을 때의 비용 포함

무엇을: 제안 하나만 쓰지 않고, 채택하지 않을 경우의 대안(현행 유지 포함)과 그때 생기는 비용·위험을 나란히 넣게 합니다.
왜: 결재권자는 한 안을 승인하는 것이 아니라 여러 선택지 중 하나를 고릅니다. 대안이 없으면 결정이 아니라 동의를 요구하는 문서가 됩니다. (실무 관행, 출처 미확인)
질문 문장:
```
이 안 외에 현행 유지와 다른 대안 하나를 나란히 놓고, 각 안을 골랐을 때 잃는 것과 위험을 같은 기준으로 비교해줘.
```

### 4-8. 초안 후 기준에 따라 자기 비평 요청

무엇을: 초안을 받은 뒤 정해진 기준(결정 사항이 드러나는가, 수치에 근거가 있는가, 대안이 있는가)으로 스스로 비평하게 하고 반영해 다시 쓰게 합니다.
왜: 같은 모델이 자기 출력에 피드백을 주고 반복 개선하는 방식이 여러 과제에서 품질을 높였습니다[7]. 다만 기준 없이 "더 좋게"라고만 하면 효과가 없으므로 기준을 줍니다.
질문 문장:
```
방금 쓴 초안을 결재권자 입장에서 다시 읽고, 결정에 필요한 정보가 빠진 부분과 근거 없는 문장을 지적한 다음 그걸 반영해서 다시 써줘.
```

### 4-9. 예상 반론 먼저 받고 본문에 반영

무엇을: 본문을 쓰기 전에 읽는 사람이 던질 반론 세 개를 먼저 받고, 각 반론에 답하는 문장이 본문 어느 항목에 들어가는지 지정하게 합니다. 4-7의 대안 비교가 "다른 선택지"를 다룬다면, 이 기법은 "이 선택지에 대한 공격"을 다룹니다.
왜: 결재권자의 질문은 대부분 반론의 형태입니다. 반론을 미리 받아 본문에 넣으면 회의에서 답하는 대신 문서가 답합니다. 자기 비평(4-8)과 달리 초안 전에 하므로 구조 자체가 반론을 담는 쪽으로 잡힙니다[7]. (실무 관행, 출처 미확인)
질문 문장:
```
본문을 쓰기 전에, 이 기획을 읽은 재무 임원이 던질 반론을 3개 먼저 써줘. 그다음 각 반론에 답하는 문장을 본문 어느 항목에 넣을지 정하고, 그 문장의 근거가 첨부 자료 어디에 있는지도 적어줘.
```

## 5. 실행 순서

1. 2절의 확인 항목 중 빠진 것을 한 개씩 묻습니다(두 개까지). 읽는 사람과 결정 사항은 거의 항상 필요합니다.
2. 아웃라인을 먼저 냅니다(4-5). 항목마다 핵심 메시지 한 줄과, 그 항목의 근거가 어느 자료에서 오는지 적습니다. 읽는 사람이 던질 반론 세 개를 함께 적고 어느 항목에서 답하는지 표시합니다(4-9). 사용자 확인 후 본문으로 갑니다. 사용자가 "한 번에"라고 하면 아웃라인을 본문 앞에 붙여 한 번에 냅니다.
3. 본문은 결론(요청 사항) 먼저 배치합니다(4-2). 첫 문단에 결정 사항·요청 내용·핵심 근거 한 줄이 들어갑니다.
4. 수치·사례는 자료에서 인용한 것만 쓰고 출처 위치를 붙입니다(4-3). 자료에 없는 값은 `[확인 필요]`로 둡니다(4-4).
5. 대안과 하지 않을 때의 비용을 한 절로 넣습니다(4-7).
6. 담당·일정·예산 칸은 사용자가 준 것만 채우고 나머지는 빈칸으로 둡니다.
7. 초안 끝에 자기 비평(4-8)을 붙입니다. 기준은 8절 점검 목록입니다.
8. 6절 형식으로 정리하고 공통 규칙을 적용합니다.

## 6. 출력 형식

형식은 네 가지이며 references/formats/plan-formats.md 에 있습니다. 기본은 형식 1(1장 품의)이고, 결재권자 없이 본인이 실행하는 계획은 형식 4(실행 계획)입니다. 어느 형식을 쓸지는 그 파일의 "선택 조건"과 references/format-profile.md 5절로 정합니다. 아래는 기본 틀과 채운 예시입니다. 결과 맨 위에 `형식: ○○ — 이유 한 줄`을 씁니다.

```
[문서 조건]
읽는 사람: ○○ / 결정 사항: ○○ 승인 여부 / 근거 자료: ○○ 파일 / 형식: ○○ 양식 준용

[아웃라인] (본문 전에 확인)
1. 결론·요청 — 핵심 메시지 한 줄 — 근거: 자료 ○ p.○
2. 배경·현황 — ... — 근거: ...
3. 방안 — ...
4. 대안 비교 — 현행 유지 / 대안 B — 근거: ...
5. 실행(담당·일정·예산) — [확인 필요] 항목: 담당자, 시행일
6. 위험과 대응 — ...

[본문]
(아웃라인 순서대로. 수치 옆에 출처 위치. 없는 값은 [확인 필요])

[자기 비평]
- 첫 문단만 읽고 결정 사항이 보이는가: 예 / 아니오(수정함)
- 출처 없는 수치: ○건 → [확인 필요]로 전환
- 대안 비교: 있음 / 없음
- [확인 필요] 목록: ○○, ○○
```

`[확인 필요]`를 없애려고 값을 채우지 않습니다. 목록으로 모아 두면 사용자가 무엇을 확인해 넣을지 바로 알 수 있습니다.

## 7. 나쁜 질문 → 고친 질문

| 상황 | 나쁜 질문 | 고친 질문 | 적용 기법 |
|---|---|---|---|
| 신규 서비스 제안 | 이런 신규 서비스를 하면 좋을 것 같은데 기획안 써줘 | 사업부장이 다음 주 회의에서 예산 편성 여부를 결정할 때 읽는 문서야. 결정 사항, 필요 인력·예산, 경쟁 서비스 대비 차별점을 앞에 배치하고, 예산 수치는 첨부 자료에 있는 것만 쓰고 없는 값은 [확인 필요]로 남겨줘 | 4-1, 4-2, 4-4 |
| 예산 증액 | 예산 늘려달라는 보고서 하나 써줘 | 재무 임원이 추가 예산 승인 여부를 결정할 때 읽어. 증액 이유, 증액하지 않았을 때의 위험, 금액과 사용처 순서로 쓰고, 금액은 첨부한 지난 분기 집행 내역에서만 인용해줘 | 4-1, 4-3, 4-7 |
| 프로세스 개선 | 업무 프로세스 개선안 초안 만들어줘 | 부서장이 현재 방식 유지와 변경 중 결정할 때 읽는 문서야. 현재 문제, 개선안, 현행 유지 대안을 나란히 비교하고, 담당자·일정은 내가 채울 자리로 남겨줘 | 4-1, 4-4, 4-7 |
| 협업 제안 메일 | 다른 팀에 협업 제안하는 메일 써줘 | 상대 팀장이 참여 여부를 답장으로 결정할 때 읽는 글이야. 요청 한 가지, 상대 팀이 얻는 것, 필요한 시간(회의 1회 30분)을 첫 문단에 넣어줘 | 4-1, 4-2 |
| 분기 보고 | 이번 분기 실적 보고서 정리해줘 | 대표가 다음 분기 방향을 결정할 때 참고하는 문서야. 목표 대비 실적, 미달 항목의 원인, 다음 분기 제안 두 가지를 앞에 넣고, 수치는 첨부 데이터에서만 가져오고 없는 항목은 비워둬 | 4-1, 4-3, 4-4 |
| 채용 요청 | 사람 더 뽑아야 하니까 요청서 써줘 | 인사팀과 본부장이 채용 인원과 시기를 결정할 때 읽어. 현재 업무량과 부족으로 생기는 문제, 채용하지 않을 경우의 대안(외주·재배치)과 한계, 필요 인원과 시기 순서로 쓰고, 업무량 수치는 내가 채울 자리로 남겨줘 | 4-1, 4-4, 4-7 |
| 업체 선정 | 업체 세 곳 비교해서 보고서 만들어줘 | 구매 임원이 한 곳을 선정할 때 읽어. 추천 업체와 이유를 맨 앞에 쓰고, 가격·일정·실적 기준 비교표를 넣고, 견적 금액은 첨부 제안서에 있는 숫자만 써줘 | 4-1, 4-2, 4-3 |
| 정책 변경 건의 | 재택근무 정책 바꾸자는 글 써줘 | 인사위원회가 변경 여부를 결정할 때 읽는 문서야. 현재 정책의 문제, 변경안, 변경할 때와 하지 않을 때의 예상 효과를 비교하고, 시행 시기와 범위는 내가 정할 자리로 비워줘 | 4-1, 4-4, 4-7 |
| 목차 먼저 받기 | 교육 프로그램 도입 기획안 써줘 | 본문 말고 목차와 항목별 핵심 메시지 한 줄씩만 먼저 줘. 항목마다 근거가 첨부 자료 어디에서 오는지도 적어줘. 확인하고 본문을 요청할게 | 4-5, 4-3 |
| 반론 미리 받기 | 이 기획안 설득력 있게 써줘 | 쓰기 전에 사업부장이 이 안에 던질 반론 3개를 먼저 써주고, 각 반론에 답하는 문장을 본문 어느 항목에 넣을지 정해줘. 그다음 본문을 써줘 | 4-9 |

## 8. 점검 목록

| 실패 | 확인 질문 |
|---|---|
| 배경이 장황하고 결론이 없다 | 첫 문단만 읽고 결재권자가 무엇을 승인해야 하는지 알 수 있는가 |
| 없는 수치·사례를 지어낸다 | 모든 수치·사례 옆에 출처가 있거나, 없으면 [확인 필요] 표시가 붙어 있는가 |
| 대안 없이 한 안만 있다 | 채택하지 않을 경우의 대안과 비교 기준이 문서에 있는가 |
| 실행 주체·일정이 비어 있다 | 누가·언제까지·무엇을 하는지 적혀 있거나, 빈칸이 [확인 필요]로 표시되어 있는가 |
| 문체가 흔들린다 | 종결 어미와 용어("~합니다"와 "~함")가 한 가지로 통일되어 있는가 |

## 9. 다음 단계

- 아웃라인 단계였으면: 사용자 확인 후 본문 요청. 반론 세 개가 아직 없으면 본문 전에 반론부터 요청(4-9)
- 본문이 나왔으면: 결과물 검토 유형으로 넘겨 "반려한다면 어떤 이유로"를 새 대화에서 묻기
- [확인 필요]가 결론을 좌우하면: 그 값의 출처를 자료조사 유형으로 확인하거나 사용자가 직접 채움
- 수치 근거가 약하면: 데이터 분석 유형으로 넘겨 첨부 데이터에서 재계산
