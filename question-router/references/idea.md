## 1. 이 업무 유형으로 오는 신호 / 아닌 경우

이 업무 유형은 아직 무엇을 할지 정해지지 않은 상태에서 선택지의 종류와 범위를 넓히는 단계입니다. "아이디어 좀", "방법 없을까", "다른 안은", "브레인스토밍", "후보를 뽑아" 같은 표현이 신호입니다. 방향이 여러 개 열려 있고, 사용자가 그중 무엇을 고를지 아직 모른다는 점이 핵심입니다.

다음은 겉모습이 비슷해도 다른 업무 유형입니다.

- 자료조사: 경쟁사 사례, 시장 수치처럼 이미 존재하는 사실을 확인하는 요청입니다. 답에 확인 가능한 출처가 필요하면 자료조사, 출처보다 발상의 폭이 중요하면 아이디어 기획입니다.
- 기획안 작성: 이미 하나로 좁혀진 안을 문서 형식으로 옮기는 요청입니다. "이 중 하나를 골랐으니 정리해 달라"는 말이 나오면 기획안 작성으로 넘깁니다.

## 2. 먼저 확인하는 것

입력에 없으면 결과를 만들기 전에 묻습니다. 한 번에 한 개씩, 두 개까지 묻습니다.

| 확인 항목 | 왜 필요한가 | 없을 때 생기는 일 |
|---|---|---|
| 제약 조건(예산·기간·인원·형식) | 제약이 있어야 그 안에서 탐색이 넓어집니다[8] | 실행 불가한 안이 섞이고, 걸러내는 데 시간이 듭니다 |
| 목적(무엇이 좋아지면 성공인가) | 목적이 다르면 좋은 안의 기준이 달라집니다 | 목적에 안 맞는 안을 두고 다시 요청하게 됩니다 |
| 이미 검토했거나 제외한 안 | 같은 안이 다시 나오는 것을 막습니다 | 첫 결과의 절반이 이미 본 안으로 채워집니다 |
| 대상(누구를 위한 안인가) | 대상별로 축을 나누는 데 필요합니다 | AI가 대상을 임의로 가정합니다 |

## 3. 첫 답이 왜 평범한가

언어 모델은 훈련 데이터에서 자주 나타나는 패턴을 재현하도록 학습되고, 후속 학습(RLHF)을 거치며 표현의 변이가 한 번 더 줄어듭니다[6]. 그래서 "아이디어 10개"라는 요청은 같은 중심 분포 안에서 표현만 바꾼 답을 반복해서 꺼내는 결과로 이어집니다.

컬럼비아 경영대학원 연구는 이 차이를 사람과 비교해 설명합니다. 사람은 각자 다른 지식 영역을 나눠 갖고 있어 같은 문제에도 다른 출발점에서 답하지만, 모델은 지식이 하나로 수렴되어 있어 기본 프롬프트로는 그 중심부에서만 답을 꺼냅니다. 같은 연구에서 페르소나를 다르게 주고 사고 과정에서 서로 다르게 만들라고 지시했을 때 고유한 아이디어 조합이 사람 집단보다 많아졌습니다[3]. 디자인 콘셉트 생성 실험에서도 역할별로 독립된 프롬프트를 준 쪽이 다양성이 높았습니다[4].

따라서 개수를 늘리는 요청은 다양성을 거의 늘리지 못합니다. 답이 만들어지는 축(관점·역할·제약·문제 정의)을 바꾸는 질문이 필요합니다. Anthropic 공식 문서도 원하는 결과의 배경·대상·제약을 명시하는 것을 기본 기법으로 안내합니다[1][2]. 이것이 "많이 내게 하지 말고, 다르게 내게 한다"의 근거입니다.

한 가지 더 확인된 것이 있습니다. AI로 낸 아이디어는 개인 수준에서는 다양해 보여도 집단 수준에서 평균값으로 수렴했고, AI가 낸 안에 대한 참가자의 책임감(내가 만든 안이라는 인식)이 대조군보다 낮았습니다[5]. AI가 낸 안을 검토 없이 채택하면 이 문제가 그대로 업무에 들어옵니다.

## 4. 질문 전략

각 기법은 "축을 바꾸는" 방법 하나씩에 해당합니다. 한 번의 요청에 기법 하나를 적용하고, 결과를 본 뒤 다른 축으로 넘어갑니다.

### 4-1. 평범한 페르소나 분산

무엇을: 유명 인물이 아니라 "은퇴 앞둔 총무팀 직원", "입사 6개월 차 신입", "외부 협력업체 담당자"처럼 평범하고 서로 다른 배경의 인물을 여러 명 지정해 각각 답하게 합니다.
왜: 페르소나마다 접근하는 지식 영역이 달라져 중심 분포 밖에서 답을 꺼내게 됩니다[3].
질문 문장:
```
은퇴를 앞둔 총무팀 직원, 입사 6개월 차 신입, 외부 협력업체 담당자 세 명이 각각 이 문제를 본다면 어떻게 다르게 접근할지 따로따로 답해줘.
```

### 4-2. 단계 분리와 명시적 차별화

무엇을: 짧은 제목만 먼저 여러 개 뽑게 한 다음, "서로 겹치지 않도록 다시 고쳐라"를 별도 요청으로 보냅니다.
왜: 단계를 나누면 이전 출력에 고착되는 정도가 줄고, 페르소나 지정과 결합하면 효과가 커집니다[3].
질문 문장:
```
먼저 제목만 5개 뽑아줘. 그다음 그 5개를 다시 보고 서로 겹치는 부분을 찾아, 각각 다른 방향으로 고쳐서 다시 써줘.
```

### 4-3. 역할별 독립 요청

무엇을: 여러 역할을 한 프롬프트에 담지 않고, 역할마다 별도 요청(또는 별도 대화)으로 답을 받은 뒤 합칩니다.
왜: 역할별 독립 프롬프트가 역할 없이 생성한 경우보다 결과의 다양성이 높았습니다[4].
질문 문장:
```
이 문제를 마케팅 담당자 입장에서만 보고 답해줘.
```
(같은 문제를 재무 담당자, 현장 직원 입장으로 각각 새로 요청합니다)

### 4-4. 대안 접근법 요청

무엇을: 방법 하나를 요청하는 대신 "이 목표를 이룰 수 있는 서로 다른 방법들"과 각각의 장단점을 요청합니다.
왜: 사용자가 인지하지 못한 대안의 존재를 드러내는 것이 이 패턴의 설계 목적입니다[7].
질문 문장:
```
이 목표를 달성할 수 있는 서로 다른 접근 방법을 나열하고, 각 방법의 장단점을 표로 비교해줘.
```

### 4-5. 제약 조건 부여

무엇을: 예산·기간·인원·형식 같은 제한을 먼저 걸고 그 안에서만 안을 내게 합니다.
왜: 선택지가 무제한이면 탐색이 얕아지고, 제약이 있으면 그 범위 안에서 더 넓게 탐색한다는 논의가 있습니다[8].
질문 문장:
```
예산 200만 원, 준비 기간 2주, 참여 인원 30명 이하라는 조건 안에서만 가능한 안으로 다시 내줘. 조건을 벗어나는 안은 빼줘.
```

### 4-6. SCAMPER 축 지정

무엇을: 대체(Substitute)·결합(Combine)·응용(Adapt)·변형(Modify)·용도 전환(Put to another use)·제거(Eliminate)·역전(Reverse) 중 하나를 지정해 그 축으로만 안을 내게 합니다.
왜: 매번 다른 조작을 지정하기 때문에 같은 질문을 반복해도 결과가 겹치지 않습니다[9].
질문 문장:
```
지금 이 서비스에서 '제거' 축으로만 생각해줘. 지금 있는 요소 중 하나를 없앤다면 무엇을 없앨 수 있고, 그러면 무엇이 달라지는지 말해줘.
```

### 4-7. HMW(How Might We) 재구성

무엇을: 문제를 "왜 안 되는가"가 아니라 "우리가 어떻게 하면 ~할 수 있을까"라는 개방형 질문으로 다시 쓰고 나서 안을 요청합니다.
왜: 특정 해법을 미리 암시하지 않는 문장으로 바꾸면 그다음 발상의 범위가 넓어집니다[10].
질문 문장:
```
'문의 응대가 느리다'는 문제를 '고객이 기다린다는 느낌 없이 답을 받게 하려면 어떻게 할 수 있을까'라는 질문으로 바꿔서, 그 질문에 대한 안을 내줘.
```

### 4-8. 의도 되묻기

무엇을: 완성된 답을 한 번에 받지 않고, 먼저 이쪽이 원하는 방향을 되묻게 한 뒤 안을 받습니다.
왜: 완성된 답이 사용자의 해석 작업을 줄여 집단 수준의 수렴을 부른다는 실험 결과가 있습니다[5].
질문 문장:
```
바로 답을 내지 말고, 먼저 내가 정말 원하는 게 무엇인지 되묻는 질문을 3개 던져줘. 내 답을 듣고 나서 안을 내줘.
```

### 4-9. 시점 전환

무엇을: 지금 시점이 아니라 과거(이미 해 봤거나 검토한 것)와 미래(1년 뒤·행사 당일) 시점에서 보게 합니다. 과거 시점은 제외 목록으로, 미래 시점은 결과 장면으로 씁니다.
왜: 같은 시점에서만 보면 이미 본 안이 다시 나옵니다. 제외 목록을 먼저 주면 그 밖에서 찾게 되고[2], 결과 장면에서 거꾸로 오면 지금 떠오르지 않는 안이 나옵니다. (실무 관행, 출처 미확인)
질문 문장:
```
지난 2년간 해 본 방식은 이거야: ○○, ○○, ○○. 이건 모두 빼고, 이 목록에 없는 방식으로만 안을 내줘.
```
```
행사가 끝난 다음 날 참가자가 동료에게 한 문장으로 설명한다면 뭐라고 말할지 먼저 3가지로 쓰고, 그 문장이 나오려면 무엇을 했어야 하는지 거꾸로 안을 내줘.
```

### 4-10. 반대 가정

무엇을: 당연하게 깔려 있는 전제(장소가 필요하다, 전원이 참석한다, 강사가 있다) 하나를 골라 "그게 없다면"으로 뒤집고 그 조건에서만 안을 내게 합니다.
왜: 전제를 그대로 두면 안이 전제 안에서만 나옵니다. 전제를 하나씩 지정해 뒤집으면 SCAMPER의 제거·역전(4-6)을 특정 전제에 집중 적용하는 효과가 납니다[9].
질문 문장:
```
이 워크숍은 '한 장소에 모인다'를 전제로 하고 있어. 모이지 않는다고 가정하면 어떤 안이 가능한지, 그 조건에서만 3개 내줘.
```

## 5. 실행 순서

1. 2절의 확인 항목 중 빠진 것을 한 개씩 묻습니다(두 개까지).
2. 문제 문장을 HMW 형태로 다시 씁니다(4-7). 사용자 문장이 이미 개방형이면 건너뜁니다.
3. 축을 두세 개 고릅니다. 기본은 대상별 페르소나(4-1) 하나, SCAMPER 조작(4-6) 하나입니다. 사용자가 이미 해 본 안을 줬으면 시점 전환(4-9)의 제외 목록을 모든 축에 적용하고, 전제가 뚜렷한 업무면 반대 가정(4-10)을 축 하나로 씁니다. 사용자가 제약을 줬으면 제약(4-5)을 모든 축에 공통 적용합니다.
4. 축마다 별도로 안을 냅니다. 축당 3~4개면 충분합니다. 개수를 늘리지 않습니다.
5. 안마다 "무엇을 실행하는가"를 한 문장으로 적어 겹침을 확인하고, 겹치는 안은 합치거나 다른 방향으로 고칩니다(4-2).
6. 6절 형식으로 정리하고, 공통 규칙(입력에 없는 값은 `[확인 필요]`, 근거 위치, 사실·추정 분리)을 적용합니다.

## 6. 출력 형식

형식은 세 가지이며 references/formats/idea-formats.md 에 있습니다. 기본은 형식 1(옵션 비교 메모)이고, 어느 형식을 쓸지는 그 파일의 "선택 조건"과 references/format-profile.md 5절로 정합니다. 아래는 기본 틀과 채운 예시입니다. 결과 맨 위에 `형식: ○○ — 이유 한 줄`을 씁니다.

```
문제 문장(다시 쓴 것): 우리가 어떻게 하면 ~할 수 있을까
적용한 제약: 예산 / 기간 / 인원 (사용자 입력)

[축 1: ○○ 입장]
1. 안 이름 — 무엇을 실행하는가 한 문장 — 이 축에서 나온 이유
2. ...

[축 2: SCAMPER '제거']
1. ...

겹침 확인: 축 1의 2번과 축 2의 1번은 실행 내용이 같아 하나로 합쳤습니다.
전제 표시: 이 안들은 "대상이 기존 고객"이라고 가정했습니다(사용자 확인 필요).
```

안을 고르거나 순위를 매기지 않습니다. 고르는 것은 사용자의 몫이고, 이 업무 유형은 선택지의 폭을 만드는 단계입니다.

채운 예시(예시용 가상 값 — 팀 워크숍, 사용자 입력: 예산 200만 원·30명·반나절·목적은 부서 간 협업):

```
문제 문장(다시 쓴 것): 우리가 어떻게 하면 다른 부서 사람과 처음으로 같이 일해 보게 할 수 있을까
적용한 제약: 예산 200만 원 / 반나절 / 30명 (사용자 입력)
제외 목록: 강사 초청 강연, 볼링·야구 관람 (사용자 입력 — 지난 2년 실시)

[축 1: 입사 6개월 차 신입 입장]
1. 부서 교환 반나절 — 다른 부서의 실제 업무 하나를 두 시간 대신 해 본다 — 신입은 다른 부서가 무슨 일을 하는지 모른다는 점에서 나옴
2. 질문 카드 점심 — 식탁마다 "그 부서에 물어보고 싶었던 것" 카드를 놓고 답을 받는다 — 신입은 물어볼 통로가 없다는 점에서 나옴

[축 2: 반대 가정 '한 장소에 모이지 않는다']
1. 부서 간 과제 릴레이 — 한 부서가 시작한 과제를 다음 부서가 이어받아 하루 안에 끝낸다 — 모이지 않아도 협업이 생기는 조건에서 나옴
2. 현장 교차 방문 — 두 부서가 서로의 근무 장소를 한 시간씩 방문한다 — 장소를 고정하지 않는 조건에서 나옴

겹침 확인: 축 1의 1번과 축 2의 2번은 "다른 부서 일을 직접 본다"로 겹쳐, 2번을 "방문"에서 "상대 부서 회의 참관"으로 고쳤습니다.
전제 표시: "부서 간 협업"을 "처음 같이 일해 보는 것"으로 좁혀 읽었습니다(사용자 확인 필요).
```

## 7. 나쁜 질문 → 고친 질문

| 상황 | 나쁜 질문 | 고친 질문 | 적용 기법 |
|---|---|---|---|
| 신제품에 넣을 기능 | 이 제품에 넣을 만한 기능 아이디어 10개 알려줘 | 사용자를 '처음 써보는 사람', '매일 쓰는 사람', '가끔 쓰는 사람' 세 유형으로 나누고, 유형마다 필요한 기능을 각각 다르게 제안해줘 | 4-1 |
| 연말 사내 행사 | 재밌는 사내 행사 아이디어 좀 줘 | 예산 300만 원, 참여 50명, 준비 3주 조건 안에서만 가능한 행사 안을 내줘. 조건을 벗어나는 안은 빼줘 | 4-5 |
| 매출 부진 대책 | 매출을 올릴 수 있는 방법을 알려줘 | '매출이 낮다'를 '기존 고객이 재구매할 이유를 어떻게 만들 수 있을까'로 바꿔서, 그 질문에 대한 안을 내줘 | 4-7 |
| 고객 이탈 | 고객 이탈 방지 아이디어 알려줘 | 이제 막 이탈을 고민 중인 고객 입장에서 한 번, 이미 경쟁사로 옮긴 고객 입장에서 한 번, 각각 따로 답해줘 | 4-1 |
| 캠페인 방향 | 마케팅 캠페인 아이디어 5개 줘 | '결합' 축으로만 생각해줘. 우리 제품과 전혀 다른 카테고리의 브랜드나 콘텐츠 하나를 골라 엮는다면 무엇과 엮을 수 있을지 말해줘 | 4-6 |
| 조직 문화 개선 | 직원들이 좋아할 만한 개선 방안을 알려줘 | 바로 답하지 말고, 지금 조직에서 실제로 불편해하는 지점이 무엇인지 되묻는 질문을 먼저 던져줘 | 4-8 |
| 비용 절감 | 비용을 줄일 수 있는 아이디어를 알려줘 | 지금 하는 일 중 하나를 없앤다면 무엇을 없앨 수 있는지, 없앴을 때 생기는 문제는 무엇인지 같이 말해줘 | 4-6 |
| 신규 사업 아이템 | 요즘 뜨는 신규 사업 아이템 알려줘 | 갓 퇴사한 직장인, 이 업계 20년 차, 전혀 다른 업계에서 온 사람 세 명이 각각 본다면 어떤 아이템을 떠올릴지 따로 답해줘 | 4-1 |
| 팀 워크숍(반복 개최) | 올해 워크숍 아이디어 좀 줘 | 작년과 재작년에 한 건 강연·볼링·야구 관람이야. 이 셋은 빼고, 이 목록에 없는 방식으로만 안을 내줘 | 4-9 |
| 신규 고객 설명회 | 설명회를 어떻게 하면 좋을까 | 설명회는 '우리가 설명한다'를 전제로 해. 우리가 한마디도 설명하지 않는다고 가정하면 어떤 형식이 가능한지, 그 조건에서만 안을 내줘 | 4-10 |

## 8. 점검 목록

| 실패 | 확인 질문 |
|---|---|
| 개수만 많고 같은 발상의 변형이다 | 이 안들 중 서로 다른 축(대상·시점·수단)에서 나온 안이 몇 개인가 |
| 표현만 다르고 본질이 같다 | 각 안의 "무엇을 실행하는가"를 한 문장으로 적었을 때 겹치는 문장이 있는가 |
| 실행 불가한 안이 섞였다 | 지금 예산·인원·남은 기간 안에서 실제로 시작할 수 있는가 |
| AI가 대상·목표를 임의로 가정했다 | 답에서 가정한 대상·목표·기준이 우리가 정한 것과 같은가 |
| AI가 낸 안을 검토 없이 채택한다[5] | 이 안 중 내가 직접 근거를 설명할 수 있는 안은 몇 개인가 |

## 9. 다음 단계

결과에 따라 아래 중 하나를 다음 질문으로 제안합니다.

- 축이 하나뿐이었으면: 다른 축(다른 페르소나, 다른 SCAMPER 조작, 시점 전환, 반대 가정)으로 한 번 더 요청
- 안이 충분히 갈렸으면: 사용자가 두세 개를 고르게 하고, 고른 안마다 "이 안이 되려면 참이어야 하는 것" 두 가지와 가장 싸게 확인하는 방법을 요청(형식 2 아이디어 카드). "잃는 것" 비교는 형식 1 표에 이미 있으므로 다시 요청하지 않습니다
- 결정권자에게 올려야 하면: 고른 안을 형식 3 결정 메모로 압축. 이때 "잃는 것"은 형식 1 표의 값을 옮겨 쓰고, 새로 추가하는 것은 압축 기준과 결정 질문뿐입니다
- 사실 확인이 필요한 안이 있으면: 자료조사 유형으로 넘겨 그 안의 전제(시장·사례·비용)를 확인
- 하나로 좁혀졌으면: 기획안 작성 유형으로 넘겨 결정 문서로 옮김
