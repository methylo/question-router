## 1. 이 업무 유형으로 오는 신호 / 아닌 경우

이 업무 유형은 이미 만든 결과물(보고서·기획안·메일·공고·계약 조항·슬라이드)에서 결함의 위치를 찾는 단계입니다. "검토해 줘", "봐 줘", "괜찮아?", "문제없어?", "빠진 것 없나"가 신호입니다. 통과·반려를 가를 결함을 찾는 것이 목적이고, 최종 승인·반려는 사람의 몫으로 남는다는 점이 핵심입니다.

다음은 겉모습이 비슷해도 다른 업무 유형입니다.

- 기획안 작성: 초안이 아직 없으면 검토가 아니라 생성입니다. 초안이 있는지가 구분 기준입니다.
- 자료조사: 결과물 안에 인용된 사실이 맞는지 밖에서 확인하는 것은 자료조사입니다. 검토는 쓰인 문장과 주장 사이의 정합성을 봅니다. 두 작업이 함께 필요하면 검토를 먼저 하고 사실 확인 항목을 자료조사로 넘깁니다.
- 퇴고·윤문: "틀렸는가"가 아니라 "더 나은 표현이 있는가"를 묻는 작업입니다. 이 업무 유형은 통과 가능한 글을 더 낫게 만드는 일이 아니라, 통과를 막을 결함을 찾는 일입니다.

## 2. 먼저 확인하는 것

| 확인 항목 | 왜 필요한가 | 없을 때 생기는 일 |
|---|---|---|
| 이 결과물을 받을 사람과 그 사람이 반려할 수 있는 이유 | 반대 독자를 지정해야 검토가 지지자 모드에서 벗어납니다[9][10] | "전반적으로 잘 썼습니다"로 끝납니다 |
| 통과 기준(무엇이 있어야 통과, 무엇이 있으면 반려) | 기준이 없으면 모델이 스스로 만족스러운 기준으로 채점합니다[5] | 사소한 문체 지적만 나옵니다 |
| 결과물의 용도와 마감(임원 보고·고객 제출·법적 효력) | 심각도 판단의 기준이 됩니다 | 치명 결함과 경미 결함이 같은 무게로 나열됩니다 |
| 사용자가 이미 아는 약점 | 아는 것을 다시 듣는 데 검토가 소모되지 않게 합니다 | 새로운 결함 탐색이 얕아집니다 |

작성자 정보와 사용자의 선호("제가 썼는데", "이 부분 마음에 드는데")는 확인하지 않습니다. 오히려 결과물에서 지우고 제출합니다(4-7).

## 3. 검토가 칭찬으로 끝나는 이유

구조적인 결과입니다. 아첨(sycophancy)은 모델이 사용자의 의견에 맞춰 답을 바꾸는 경향을 가리키는 용어로 자리 잡았고[3], 무엇을 아첨으로 볼지는 연구자 사이에서도 갈립니다[8]. Anthropic의 아첨 연구는 다섯 개 AI 어시스턴트가 사용자가 표명한 의견에 맞춰 피드백의 긍정성을 바꾼다는 점을 확인했습니다. 같은 논증에 대해 사용자가 "마음에 든다"고 하면 설득력 있다고, "마음에 안 든다"고 하면 설득력이 부족하다고 평가가 바뀌었습니다. 이 경향은 인간 평가자가 자기 신념을 확인해 주는 응답을 선호하는 훈련 과정(RLHF)에서 비롯됩니다[1][2].

요청의 틀도 영향을 줍니다. "검토해 줘"라는 협력적 요청은 모델을 지지자 위치에 두지만, 결함을 찾는 역할을 명시하면 출력이 문제 탐지 쪽으로 이동합니다[9][10]. 집단 의사결정 실험에서도 반대 역할(devil's advocate)을 맡은 모델이 참가자의 재검토를 끌어냈습니다[6]. 기준 없는 자유 판단도 문제입니다. 판단 차원을 독립 항목으로 쪼개 강제 비교시키는 구조화된 평가가 자기 선호 편향을 줄였습니다[5]. 두 안을 비교할 때는 내용이 아니라 제시 순서에 따라 선호가 갈리는 위치 편향이 다수 모델에서 확인되었습니다[4].

한 가지 더 있습니다. 같은 모델이 외부 피드백 없이 자기 답을 재검토하면 오류를 놓치거나 품질이 오히려 떨어지는 경향이 보고되었습니다[7]. 초안을 만든 대화에서 그대로 "검토해 줘"라고 하면 이 함정에 들어갑니다. 그래서 검토는 새 대화에서, 고치지 말고 찾게만 하고, 반대 독자와 통과 기준을 준 상태로 시킵니다.

## 4. 질문 전략

### 4-1. 반대 독자 지정

무엇을: 검토자를 저자를 돕는 조력자가 아니라 그 결과물을 반려할 권한과 동기를 가진 인물로 지정합니다.
왜: 역할 설정이 모델의 행동과 어조를 바꾸고[10], 적대적 틀이 협력적 틀보다 문제 탐지에 유리하다고 보고됩니다[9].
질문 문장:
```
당신은 이 보고서를 반려할 권한을 가진 결재권자입니다. 승인 여부를 먼저 정하지 말고, 반려할 근거부터 찾으십시오.
```

### 4-2. 통과 기준 사전 명시

무엇을: "잘 썼는지"를 자유 판단에 맡기지 않고 통과·반려를 가르는 조건을 항목으로 미리 제시합니다.
왜: 항목별 강제 판정이 판정 편향을 줄입니다[5]. 기준이 없으면 모델이 관대한 기준을 스스로 만듭니다.
질문 문장:
```
다음 5개 조건(수치 근거 명시, 결론과 데이터 일치, 위험 언급, 대안 비교, 용어 일관성)을 각각 충족/미충족으로만 답하십시오.
```

### 4-3. 심각도 등급 강제

무엇을: 지적한 문제마다 치명/중대/경미 등급을 붙이게 합니다.
왜: 등급이 없으면 지적하기 쉬운 표면 문제(오탈자·어투)만 나열됩니다. 치명 등급이 없다면 그 이유를 설명하게 해서 "찾지 않은 것"과 "없는 것"을 구분합니다. (실무 관행, 출처 미확인)
질문 문장:
```
지적 사항마다 [치명/중대/경미]를 붙이고, 치명 등급이 하나도 없다면 그 이유를 설명하십시오.
```

### 4-4. 위치·근거 인용 강제

무엇을: 문제를 지목할 때 원문 문장을 그대로 인용하게 합니다.
왜: 인용을 요구하면 추상적 총평과 지어낸 지적이 줄고, 모델이 실제 본문을 근거로 답했는지 사용자가 바로 확인할 수 있습니다[9].
질문 문장:
```
문제를 지적할 때마다 해당 문장을 원문 그대로 인용하고, 인용할 수 없는 지적은 하지 마십시오.
```

### 4-5. 고치지 말고 찾게만 하기

무엇을: 한 요청에서 결함 발견과 수정을 같이 시키지 않고 먼저 결함 목록만 받습니다.
왜: 지적과 수정을 한 번에 시키면 수정안을 만드는 데 집중하면서 원래 결함을 얼버무릴 위험이 커집니다[7].
질문 문장:
```
지금은 수정하지 마십시오. 문제 목록만 만들고, 각 항목에 왜 문제인지만 적으십시오.
```

### 4-6. 새 대화에서 검토

무엇을: 초안을 만든 대화와 검토 대화를 분리합니다.
왜: 이전 대화의 의견과 어조가 검토에 영향을 주며, 새 대화가 이 영향을 줄이는 방법으로 제시됩니다[11]. 같은 대화 안에서는 저자가 누구인지, 이미 어떤 평을 했는지를 계속 참조합니다.
질문 문장:
```
(새 대화에서, 작성 과정 언급 없이) 아래 문서를 처음 보는 검토자 입장에서 평가하십시오.
```

### 4-7. 작성자 정보와 선호 지우고 제출

무엇을: "제가 쓴 건데", "이 부분 마음에 드는데" 같은 표현을 빼고 결과물만 제출합니다.
왜: 사용자의 선호 표명만으로 같은 텍스트에 대한 피드백의 긍정성이 바뀝니다[1][2].
질문 문장:
```
다음 제안서를 평가하십시오. (작성자나 선호 여부 언급 없이 본문만 붙여 넣음)
```

### 4-8. 순서 바꿔 재확인

무엇을: 두 안을 비교시킬 때 제시 순서를 바꿔 다시 물어 순서가 판단을 바꾸는지 확인합니다.
왜: 위치 편향이 다수 모델에서 확인되었고, 상위 모델도 순서를 바꾸면 결론이 흔들리는 비율이 무시할 수 없는 수준입니다[4].
질문 문장:
```
A안과 B안 중 어느 쪽이 나은지 판단한 뒤, 이번에는 B안을 먼저 제시하고 같은 질문에 다시 답하십시오. 결론이 바뀌면 그 이유를 설명하십시오.
```

### 4-9. 결함 종류 분류 강제

무엇을: 지적한 결함마다 사실 오류 / 근거 부족 / 누락 중 하나로 분류하게 합니다. 심각도(4-3)와는 다른 축입니다. 심각도는 "얼마나 치명적인가", 종류는 "무엇이 잘못되었는가"입니다.
왜: 종류를 나누면 다음 행동이 정해집니다. 사실 오류는 원자료 대조, 근거 부족은 자료 추가, 누락은 항목 신설입니다. 종류 없이 나열하면 수정 요청이 "고쳐줘" 한 마디로 뭉뚱그려집니다[5]. (분류 자체는 실무 관행, 출처 미확인)
질문 문장:
```
지적마다 [사실 오류 / 근거 부족 / 누락] 중 하나로 분류하십시오. 사실 오류는 본문 문장과 원자료의 어느 부분이 어긋나는지, 근거 부족은 어떤 자료가 있어야 성립하는지, 누락은 어떤 항목이 빠졌는지 적으십시오.
```

### 4-10. 원자료 함께 제출

무엇을: 검토 대상 문서만 넣지 않고, 그 문서가 근거로 삼은 원자료(데이터 파일·이전 보고·회의록)를 같이 넣고 본문과 원자료를 대조하게 합니다.
왜: 원자료 없이는 검토자가 본문 내부의 정합성만 볼 수 있고, 수치가 원자료와 다른지는 알 수 없습니다. 인용 우선 확인은 원문이 있을 때만 작동합니다[9]. 원자료가 없으면 사실 확인 항목이 전부 자료조사 유형으로 넘어갑니다.
질문 문장:
```
첨부한 원자료(실적 데이터)와 보고서를 대조해서, 보고서의 수치·인용 중 원자료와 다르거나 원자료에 없는 것을 문장 단위로 지적하십시오. 원자료에 있는 것은 '일치'로 표시하십시오.
```

### 4-11. 반대 독자 바꿔 가며 재검토

무엇을: 같은 결과물을 결재권자, 실행 담당자, 최종 수신자(고객·직원) 세 입장에서 각각 따로 검토시킵니다. 한 요청에 한 독자만 지정합니다.
왜: 독자마다 반려 이유가 다릅니다. 결재권자는 근거와 비용, 실행 담당자는 일정과 인력, 최종 수신자는 자기에게 생기는 변화를 봅니다. 한 독자로는 그 독자가 보지 않는 결함이 남습니다[10]. 9절의 "결함이 없으면 다른 반대 독자로"를 처음부터 적용하는 방법입니다.
질문 문장:
```
이번에는 이 안을 실제로 실행해야 하는 현장 담당자 입장에서만 읽으십시오. 실행 단계에서 막히는 지점을 문장 단위로 지적하십시오.
```

## 5. 실행 순서

1. 2절의 확인 항목 중 빠진 것을 한 개씩 묻습니다(두 개까지). 반대 독자와 통과 기준이 우선입니다.
2. 결과물에서 작성자 정보와 선호 표현을 지웁니다(4-7). 초안을 만든 대화라면 새 대화에서 하도록 안내하고, 새 대화에는 결과물과 함께 원자료를 넣게 합니다(4-6, 4-10). 원자료가 없으면 "원자료 없음 — 수치 대조 생략"을 결과 맨 위에 적습니다. 같은 대화에서 해야 하면 "이 검토는 작성 과정을 잊고 처음 보는 독자로 수행합니다"를 결과 맨 위에 적고 진행합니다.
3. 반대 독자를 지정하고(4-1) 통과 기준을 항목으로 적습니다(4-2). 사용자가 기준을 주지 않았으면 8절 점검 목록을 기본 기준으로 씁니다.
4. 결함만 찾습니다(4-5). 수정안을 쓰지 않습니다. 항목마다 원문 인용(4-4), 왜 문제인지, 심각도(4-3), 종류(4-9)를 붙입니다. 원자료가 있으면 사실 오류 항목에 원자료 위치를 함께 적습니다(4-10).
5. 치명 등급이 없으면 그 이유를 적습니다. "결론이 성립하려면 참이어야 하는 전제 중 본문에서 검증되지 않은 것"을 한 번 더 찾습니다.
6. 사실 확인이 필요한 인용·수치는 "사실 확인 필요" 목록으로 분리해 자료조사 유형으로 넘길 수 있게 합니다.
7. 6절 형식으로 정리하고 공통 규칙을 적용합니다. 최종 승인·반려는 쓰지 않습니다.

형식은 세 가지이며 references/formats/review-formats.md 에 있습니다. 기본은 형식 1(결함 로그)이고, 어느 형식을 쓸지는 그 파일의 "선택 조건"과 references/format-profile.md 5절로 정합니다. 아래는 기본 틀과 채운 예시입니다. 결과 맨 위에 `형식: ○○ — 이유 한 줄`을 씁니다.

```
검토 조건: 반대 독자 ○○ / 통과 기준 ○개 / 용도 ○○ / 새 대화 여부 ○
```

```
| 4 | 경미 | 누락 | "시행 시기는 추후 결정" | 시행 범위(전 부서·일부 부서)가 빠져 있어 결정 단위가 불명확 | 5문단 1문장 |
```

## 8. 점검 목록

| 실패 | 확인 질문 |
|---|---|
| "전반적으로 잘 썼습니다"로 끝남 | 몇 번째 문단, 몇 번째 문장에 문제가 있는지 답이 나오는가 |
| 사소한 문체·오탈자 지적만 함 | 지적 중 결재나 계약에 영향을 줄 만큼 중대한 것이 있는가 |
| 큰 논리 구멍을 보지 못함 | 결론이 성립하려면 참이어야 하는 전제 중 본문에서 검증되지 않은 것은 무엇인가 |
| 본문에 없는 문제를 지어냄 | 지적한 문장을 본문에서 원문 그대로 인용할 수 있는가 |
| 작성자 의견에 동조함 | 사용자 의견과 "제가 썼다"를 지우고 다시 제시해도 같은 결론이 나오는가 |
| 결함이 무엇인지 뭉뚱그려짐 | 지적마다 사실 오류·근거 부족·누락 중 무엇인지, 그에 따라 다음 행동(대조·자료 추가·항목 신설)이 정해지는가 |

## 9. 다음 단계

- 치명·중대 결함이 있으면: 결함 번호를 지정해 수정 요청(수정은 별도 요청으로, 결함 목록과 분리)
- 사실 확인 필요 항목이 있으면: 자료조사 유형으로 넘겨 원출처 대조
- 두 안 중 고르는 검토였으면: 순서를 바꿔 한 번 더(4-8), 그리고 "고르지 않은 안에서 잃는 것"을 같은 기준으로 비교
- 결함이 없다고 나왔으면: 다른 반대 독자(예: 결재권자 대신 실행 담당자, 최종 수신자)로 한 번 더 검토(4-11)
- 원자료 없이 검토했으면: 원자료를 넣고 수치 대조만 다시 요청(4-10)
